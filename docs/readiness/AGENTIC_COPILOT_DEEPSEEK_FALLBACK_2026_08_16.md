# Agentic AXXESS Copilot: DeepSeek Fallback for OpenAI Failures — 2026-08-16

Tracked as **A-138** in `docs/readiness/ACTIONABLES_READINESS_MATRIX.md`; ledger entry **#69** in
`docs/readiness/FOUNDER_BUG_CLOSURE_LEDGER_2026_07_31.md`. This document is the full evidence-chain
record for both, per this repo's standing evidence discipline (CLAUDE.md).

## External signal

Founder ran live HITL testing on `landing.triaxisventures.com` immediately after the genuinely
agentic AXXESS Copilot sprint's own production deploy (PR #250, merge commit `d48f27b`). Screenshots
of the chatbot widget on the Executive Dashboard showed every single message — a plain "Hello," the
multi-step auto-tool prompt, and the critical-tool-pause prompt, all three taken directly from that
sprint's own just-published HITL checklist — returning the identical text:

> OpenAI / ChatGPT request failed (429). This response was not generated by a live model call; treat
> it as unverified.

This is `openAiProvider.ts`'s own internal diagnostic string, displayed verbatim as the assistant's
chat reply. The chatbot was, in effect, completely non-functional on first live use.

## Product decision

Two separate, real problems were present and were fixed as two separate same-day commits.

### 1. Display bug: the raw diagnostic string reaching the user

`agenticChatLoop.ts`'s low-confidence branch (`completion.confidence < 0.62`, the sentinel this
codebase already uses for "not a live model call" — missing key, budget-guard skip, non-200
response, empty content) returned `completion.text` unfiltered as the turn's final reply. For the
OpenAI adapter, that field *is* the raw diagnostic prose on failure. `ChatbotPanel.tsx`'s existing
legacy `/api/ai` path already filters this exact case client-side (`payload.confidence < 0.62` →
"AXXESS Copilot's AI provider is temporarily unavailable. Try again shortly."), but the new agentic
wire response (`{status:"final", reply, steps, costUsd}`) carries no confidence field at all for the
client to filter on — the substitution has to happen server-side, at the source.

**Fix** (commit `3526a6c`): `agenticChatLoop.ts` now substitutes the identical honest message before
the raw text ever leaves the loop. New regression test in `agenticChatLoop.test.ts` asserts the
"429" and "not generated by a live model call" substrings never appear in a reply.

### 2. No real availability: OpenAI was genuinely rate-limited, with no fallback

This ledger's own item #67 (2026-08-02) already flagged the underlying gap and explicitly left it
open: *"why OpenAI is returning 429 in the first place... not diagnosed."* Today's incident is a
direct recurrence of that same open thread, now hitting the newly-shipped agentic loop, which had
exactly one provider and no failover path at all.

Founder asked: *"Can we route AI requests through Kimi/Deepseek through OpenRouter (already
configured) — Keeps costs very low."* Real research (not assumption) was done before implementing,
given this reverses a decision explicitly stated as a non-goal in the just-shipped sprint
("Kimi/DeepSeek tool-calling: `supportsToolCalling: false`, stated not silently omitted"):

- **DeepSeek V3** (`deepseek/deepseek-chat`, already configured here as provider `"deepseek"`) has
  reliable native tool-calling — confirmed by DeepSeek's own API docs
  ([api-docs.deepseek.com/guides/tool_calls](https://api-docs.deepseek.com/guides/tool_calls/)) and
  its standing as one of OpenRouter's most-used tool-calling models in production.
- **Kimi K2** (already configured here as `"kimi"`) has a documented, reproducible bug: OpenRouter
  advertises tool support for it, but tool calls don't reliably fire in practice
  ([Zed Industries GitHub issue #34761](https://github.com/zed-industries/zed/issues/34761),
  [detailed community writeup](https://gist.github.com/ben-vargas/c7c9633e6f482ea99041dd7bd90fbe09)).
  This is exactly the "silently-ignored tools param = a real capability lie" risk that the
  `supportsToolCalling` flag exists to prevent. **Kimi's flag stays `false`.**

Founder confirmed scope via two clarifying questions before any code was written: **DeepSeek only**
(not Kimi), and **fallback-only** — OpenAI stays primary; DeepSeek is tried only when OpenAI's own
response is a non-live-call, never as a cost-driven default.

## What changed

- **`src/services/ai/providers/openRouterProvider.ts`** — gained the identical tool-calling support
  already shipped in `openAiProvider.ts` this same session: `tools`/`tool_choice:"auto"` included in
  the request only when `request.tools?.length` (omitted entirely otherwise, so `kimi` — whose config
  keeps `supportsToolCalling:false` — never receives a `tools` param at all); response parsing widened
  to read `tool_calls`, with malformed JSON arguments fed back as a `__parseError` payload rather than
  thrown; the empty-response check widened to `!text && toolCalls.length === 0` (OpenAI-compatible
  APIs can legitimately return `content: null` alongside `tool_calls`).
- **`src/services/ai/model-routing-policy.ts`** — `deepseek.supportsToolCalling` flipped `false` →
  `true`, with a comment citing the DeepSeek-docs/OpenRouter-usage evidence above. `kimi` stays
  `false`, with a comment citing the two Kimi K2 source URLs, so a future session doesn't silently
  flip it back without re-checking whether the underlying bug has actually been fixed upstream.
- **`src/services/chatbot/agenticChatLoop.ts`** — new `resolveDeepSeekAdapter(env)` (mirrors
  `resolveOpenAiAdapter`); new `completeWithFallback(pair, request, classification)` helper: calls
  the primary (OpenAI) first, and only if its confidence is below the 0.62 sentinel *and* a
  configured fallback exists, calls the fallback (DeepSeek) once, summing `actualCostUsd` from both
  attempts. `runAgenticChatTurn` only ever constructs a fallback adapter if the tenant's own AI
  routing policy actually allows `"deepseek"` (`policy.allowedProviders.includes("deepseek") &&
  !policy.blockedProviders.includes("deepseek")`) — a policy-restricted tenant is never silently
  routed around its own provider block. The top-of-turn eligibility gate (refuses to start the turn
  at all if OpenAI itself is disallowed, or the prompt is restricted-sensitivity without policy
  approval) is unchanged; DeepSeek is a failure-mode fallback, never an alternate entry path.

## What did not change

- Kimi K2's `supportsToolCalling` stays `false` — this sprint deliberately does not attempt to fix
  or work around its OpenRouter tool-calling bug.
- OpenAI remains the primary/default provider for every agentic turn; DeepSeek is never selected
  first, regardless of cost.
- No change to the tenant AI routing policy's own provider-selection logic
  (`selectTenantModelRoute`) used elsewhere in the app — this fallback is local to the agentic loop.
- No change to Hootsuite, persisted chat history, real streaming, or `query_external_model` access —
  all still explicit non-goals from the original sprint.

## What was verified

```
pnpm run typecheck   -> 0 errors
pnpm run lint         -> 0 warnings
pnpm run build        -> clean production build
```

Targeted `vitest run` across `openRouterProvider.test.ts`, `openAiProvider.test.ts`,
`agenticChatLoop.test.ts`, `tenantModelPolicy.test.ts`: **67/67 passing**, including:

- 4 new tool-calling tests for `openRouterProvider.ts` (tools/tool_choice omitted when absent,
  included with `tool_choice:"auto"` when present, a `tool_calls`-only response parses without
  tripping the empty-content branch, malformed JSON args handled without throwing) — mirroring the
  4 equivalent tests already added to `openAiProvider.test.ts` this session.
- 4 new fallback-behavior tests for `agenticChatLoop.ts`: OpenAI failure + DeepSeek succeeds (the
  DeepSeek answer drives the turn, cost sums both attempts); OpenAI failure + DeepSeek not configured
  (no fallback call attempted, honest unavailable message); OpenAI failure + tenant policy blocks
  deepseek (fallback never called even though otherwise configured); a normal high-confidence OpenAI
  answer never touches the fallback adapter at all (regression guard against firing it needlessly).

## What remains partial

The fallback path has been exercised against mocked adapters in unit tests, not yet against a live
OpenAI 429 in production with a real OpenRouter credential in play. **Confidence: 88%**, not higher,
pending that one live re-confirmation — the specific outstanding HITL step is: send a chatbot message
on `landing.triaxisventures.com` while OpenAI is genuinely rate-limited (or with the OpenAI key
temporarily rotated out) and confirm a real DeepSeek-backed answer returns instead of the
"temporarily unavailable" message.

## Status

**Closed** as a same-day fix for both root causes. **Founder-facing verification still outstanding**:
the live re-confirmation described above.
