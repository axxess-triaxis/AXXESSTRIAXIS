# HITL Audit — Human Decision Visibility in Last 15 Merged PRs

> **Point-in-time snapshot.** Written 2026-09-27, covering merged PRs #353-#365 only. Not refreshed for PRs #366 onward;
> do not read its ratios as describing the repository's current process.

**What this audit looks for:** Evidence that a *human* made a non-trivial call — a stated tradeoff,
a named alternative that was considered and rejected with a reason, a scoping boundary set by a person,
an explicit go/no-go, or a correction of prior AI output — versus a PR that reads as AI-generated
content merged without any visible human judgment recorded in the branch's commit bodies, ledger entries,
or referenced docs.

**What "no visible HITL" means here:** It does not mean no human was involved. It means the
repository itself — commit bodies, ledger, linked docs — does not surface evidence of a human making
a non-trivial call. For automated Dependabot PRs the concept is inapplicable by design.

**Evidence sources checked per PR:**
1. Merge commit message body
2. Branch commit message body (full `%s%n%n%b`)
3. Referenced entries in `docs/readiness/FOUNDER_BUG_CLOSURE_LEDGER_2026_07_31.md`
4. Referenced entries in `docs/readiness/DECISION_OUTCOME_LEDGER.md`
5. `CLAUDE.md` — standing HITL policy (founder = named HITL authority)
6. `Co-Authored-By` attribution — used as a signal of AI involvement, not proof of human absence

**Standing HITL policy (from `CLAUDE.md`):**
> *Sudipta Koushik Sarmah, Founder and Managing Director, is the HITL (human-in-the-loop) authority.*
> *If a step requires HITL action (real login, real payment, credentialed third-party console access),
> say so and hand it back rather than fabricating the result.*

The repo's stated model is therefore: AI does the implementation work, founder makes the calls. The
audit question is whether the repository's own evidence trail shows that second part actually happened.

**Classification key:**
- `human-reviewed decision` — repository evidence shows a human made at least one non-trivial call
  (a stated tradeoff, a named rejection, a scoped boundary, an explicit go/no-go, a correction of AI output).
- `no visible HITL` — no such evidence in the accessible repository record; change reads as AI-authored
  and merged without a recorded human judgment call.
- `n/a – automated` — fully machine-generated Dependabot PR; HITL concept does not apply.

## Per-PR Findings

### PR #365 — `docs(readiness): close ledger #72 — build 3 swapped in, submitted for App Store review`

**Classification: `human-reviewed decision`**

**Reasoning:**
The commit body states: *"Founder swapped the App Store Distribution page's attached build from Build 1
(broken icon) to Build 3 (real icon) and submitted for full App Store review — screenshot confirmed."*
This is a **credentialed-console HITL action** — the founder physically navigated App Store Connect,
swapped the attached build, and hit submit. No AI can do this; App Store Connect requires Apple ID
authentication and the specific distribution page state only the account holder controls. The ledger
entry (item #72 in `FOUNDER_BUG_CLOSURE_LEDGER_2026_07_31.md`, line 179) records the exact submission
ID (`4166eadf-c323-4c00-8b35-54f73802373d`), timestamp (2026-09-03 7:25 PM), and the visual confirmation
the founder performed (thumbnail showing the real logo in the "Items Submitted" view). The PR is a
documentation commit recording a human action the human themselves took.

**Human decision visible:** The founder's choice to swap to Build 3 rather than create Build 4 from
scratch, and the timing of the submission, are both founder-controlled. No alternative was rejected
in writing, but the action itself — a credentialed console operation with screenshot confirmation —
is unambiguous HITL evidence.

### PR #364 — `docs(readiness): ledger #72 — iOS default-icon fix, wasted review cycle, real fix verified`

**Classification: `human-reviewed decision`**

**Reasoning:**
The commit body names a specific remaining HITL step that the AI explicitly declined to resolve
autonomously: *"Flags the one remaining HITL step: the App Store Distribution page's 'iOS App Version
0.7' is still attached to Build 1, needs manual swap to Build 3 before resubmitting for full App Store
review."* This is the AI handing a scoped action back to the human rather than claiming completion.

More substantively, the ledger entry it documents (item #72, `FOUNDER_BUG_CLOSURE_LEDGER_2026_07_31.md`,
line 177) records a **specific decision attributed to the founder**: *"IOS_UPLOAD_TO_TESTFLIGHT set to
false, workflow triggered as build 0.7.0 (3) in validate-only mode — confirmed via direct log inspection
[...]. Only after that confirmed clean was IOS_UPLOAD_TO_TESTFLIGHT flipped back to true and the same
build number re-triggered for real."* The commit body for PR #363 (the code change this doc PR
describes) also states: *"IOS_UPLOAD_TO_TESTFLIGHT set to false for a validate-only real-CI run before
spending another Apple review cycle on this, per explicit founder decision after the wasted build 2
submission."*

**Human decision visible:** The validate-only-first strategy (run CI with upload disabled to confirm
the icon fix works on the real macOS runner before burning another Apple review cycle) is attributed
to an explicit founder decision, not an AI default. The founder made a stated tradeoff — a slower,
two-run release process in exchange for not wasting a third review cycle.

### PR #363 — `fix(mobile): darwin architecture support for sharp + fatal icon-gen failures`

**Classification: `human-reviewed decision`** *(partial — one clear HITL signal, one implicit)*

**Reasoning:**
Two decisions are documented in this PR's commit body:

**Decision 1 (explicit HITL):** The commit body states: *"Cannot fully verify the darwin fix locally
(no Mac) — IOS_UPLOAD_TO_TESTFLIGHT set to false for a validate-only real-CI run before spending
another Apple review cycle on this, per explicit founder decision after the wasted build 2 submission."*
This is a named tradeoff with explicit attribution to a founder decision: test on real CI with the
upload disabled before spending an Apple review cycle. The alternative (ship directly with upload
enabled) was rejected because of a prior wasted review cycle. The reasoning chain — prior failure →
explicit decision to de-risk → validate-only protocol — is visible and attributed to a person.

**Decision 2 (implicit scoping):** The `generateIosAppIcon()` function's splash-screen scope was
bounded in PR #362: *"Scoped to the icon only [...] Capacitor's own scaffolded splash screen is
snapshotted before generation and restored after, so it ships exactly as cap add ios would have
produced it, unchanged by this fix."* That scoping decision is not re-stated in PR #363's commit body,
but the PR respects it — no attempt was made to fix the splash screen as part of the darwin fix.

**Caveat:** The `Co-Authored-By: Claude Sonnet 5` attribution appears on this commit and on most
commits in this window. This is standard for AI-pair-authored work; it does not by itself indicate
the human was absent, but it does mean the decision trail in the commit body is the *only* place to
find human judgment. The validate-only-first attribution ("per explicit founder decision") is the
sole marker distinguishing this as a human-reviewed call rather than an AI-autonomous one.

### PR #362 — `fix(mobile): generate the real AXXESS icon for iOS instead of Capacitor's default`

**Classification: `human-reviewed decision`** *(three distinct HITL signals)*

**Reasoning:**
This is the most evidence-rich PR for HITL signals in the window:

**Signal 1 — Scope boundary on splash screen (AI deferred to human review):** The commit body states:
*"Scoped to the icon only: the same generate --ios call also regenerates the splash screen from
resources/splash.png, which is a byte-for-byte duplicate of icon.png, below Apple's recommended
2732x2732 splash minimum, and was never reviewed as an actual splash design."* The reasoning for
not fixing the splash is stated explicitly — it's a byte-for-byte duplicate of the icon and was
never reviewed as a real design. This is a scope decision with a named reason for the rejection of the
broader fix. An AI acting autonomously would likely just fix both.

**Signal 2 — Correction of prior AI-generated claim:** The PR corrects a false claim in
`CODEBASE_DEBLOAT_SPRINT2_EVIDENCE_ARTIFACT_AUDIT_2026_08_12.md`: *"A prior audit doc [...] claiming
otherwise was never actually verified."* The commit body directly names the AI-authored artefact as
containing a false claim, and the correction is presented as the result of *"confirmed by direct
inspection, not assumption."* This is the human (or a subsequent AI session acting on human-found
evidence) overriding a previous AI output.

**Signal 3 — Staged verification protocol before burning a review cycle:** The commit body states:
*"Not yet verified: the actual Linux CI runner in mobile-capacitor-release.yml's ios-production-release
job — triggering that next before considering this closed, since this repo's own iOS pipeline history
(ledger #71) has repeatedly shown local/Windows behavior does not always match the real macOS/Linux
CI runners."* This deferred-merge-until-CI-verified practice, referencing the failure history, shows
a human-informed risk model guiding the release sequence rather than shipping immediately on local
verification passing.

**Caveat on who set scope:** The splash boundary and the staged-verification protocol are *written*
by the AI, but they reference human-established evidence (the prior icon failure, ledger #71's history).
The clearest unambiguous human signal is still PR #365's App Store Connect action. Here, the signals
are all mediated through AI-authored text that claims to reflect human-established constraints.

## Cross-cutting observations

### 1. The HITL signals are real but all AI-mediated

Every "human-reviewed decision" finding relies on *AI-written text that attributes a decision to the
founder*. The clearest unambiguous human signal in the entire window is PR #365 — an App Store Connect
action that a human physically performed. All other signals are phrases like "per explicit founder
decision" or "founder swapped the build" appearing in commit bodies written by `Claude Sonnet 5`
(per `Co-Authored-By`). These attributions are consistent with the stated operating model in `CLAUDE.md`
("founder is the HITL authority"), and the specificity of details like the submission ID and the
validate-only protocol make fabrication unlikely. But they are not independently checkable from
the repository alone — there are no PR review comments, no approval threads, no issue discussions,
no back-and-forth exchanges visible in the git record. The HITL happened in conversation, not in the
repository, and the only trace is the AI's own written account.

### 2. The `Co-Authored-By: Claude Sonnet 5` marker is on every substantive commit

Every non-Dependabot commit in this window carries `Co-Authored-By: Claude Sonnet 5
<noreply@anthropic.com>`. This is consistent with the AI writing all commit bodies, which means
all the decision-attribution language ("per explicit founder decision," "founder confirmed,"
"named HITL step") is AI-authored. There is no commit in this window where the founder wrote the
commit body themselves. This is not per se a problem — CLAUDE.md explicitly defines the operating
model this way — but it means an external auditor reading the repository cannot distinguish between
a founder decision that was discussed and then documented by the AI, and a decision the AI invented
and attributed to the founder after the fact. The repository contains no counter-evidence to the
AI's attributions, but also no independent confirmation of them.

### 3. The Dependabot major version bump (#359) is the clearest gap

PR #359 bumps `@capacitor/android` from `7.6.7` to `8.5.0` — a major version change. Capacitor's
own versioning policy treats major bumps as potentially breaking for native plugin APIs. No review
comment, no commit body note, and no ledger entry records a human assessing whether the major API
surface change affects this repo's usage of `@capacitor/android`. The PR was merged without any
recorded human judgment. This is the one case in the window where the *absence* of HITL is a
concrete risk, not just a process gap.

### 4. The window is narrow and homogeneous

All 5 human-authored PRs are from a single incident sequence (iOS icon → darwin fix → ledger closeout
→ Android closeout). This is not a representative sample of the repo's development process. A window
that included feature PRs, security changes, or migration work would likely produce very different
ratios and evidence patterns. These findings should not be generalised beyond this specific 15-PR
window.
