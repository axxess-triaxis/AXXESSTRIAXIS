## 1. Why this redesign — the evidence chain

**External signal**: founder review of the live Executive Dashboard (screenshots reviewed directly, 2026-08-01) found the page is structurally ~80% governance/admin-oriented and ~20% performance-oriented.

**Product decision** (`Founder-stated`): AXXESS's actual product positioning is "50% company brain + 30% AI enterprise operating & execution infra + 20% compliance/governance/policy/audit engine." A dashboard that is 80% governance-weighted is inverted relative to this positioning and should be corrected.

**Verified against current code**: `src/features/dashboard/DashboardSection.tsx` (661 lines) is a single flat vertical JSX stack in a hardcoded, non-scored order — Onboarding checklist → Golden Path journey → Tenant Health Command Center → 4 demo-only KPI cards → 3 static "AI Router/Live Ops/External Signals" cards → demo-only governance alert cards → Recent Activity + Workflow Timeline → Priority Actions → Strategic Objectives + AI Recommendations → Project Health + Risk Heatmap → demo-only charts. Position is determined purely by source order in JSX; nothing is scored, nothing re-flows. A repo-wide search confirms **zero existing implementation** of any Priority×Criticality concept anywhere in the codebase — `src/domain/entities.ts:3` defines `PriorityLevel` as a 4-value string enum (`"low" | "medium" | "high" | "urgent"`), not a 1-5 integer scale, and no `Criticality` type exists at all.

**Shipped artifact**: this plan, and the phased implementation it describes (not yet built).

**Verification status**: this document itself — code implementation has not started.

## 4. Scoring engine — full logic and rationale

### 4.1 Core types

```ts
export type CriticalityBand = "green" | "yellow" | "orange" | "amber" | "red";
export type PriorityLevel1to5 = 1 | 2 | 3 | 4 | 5;

const CRITICALITY_WEIGHT: Record<CriticalityBand, 1 | 2 | 3 | 4 | 5> = {
  green: 1,
  yellow: 2,
  orange: 3,
  amber: 4,
  red: 5,
};

export function computeScore(priority: PriorityLevel1to5, criticality: CriticalityBand): number {
  return priority * CRITICALITY_WEIGHT[criticality]; // range 1-25
}
```

This is a full 5×5 risk matrix (both axes continuous 1-5) — directly matching the standard ISO-31000-style risk matrix cited in R3, with no residual axis asymmetry.

### 4.2 Full 25-cell score grid (for reference — every tile's score is one of these)

| Priority ↓ / Criticality → | Green(1) | Yellow(2) | Orange(3) | Amber(4) | Red(5) |
|---|---|---|---|---|---|
| **1** | 1 | 2 | 3 | 4 | 5 |
| **2** | 2 | 4 | 6 | 8 | 10 |
| **3** | 3 | 6 | 9 | 12 | 15 |
| **4** | 4 | 8 | 12 | 16 | 20 |
| **5** | 5 | 10 | 15 | 20 | 25 |

### 4.3 Why the founder's original OR-based gate proposal was rejected (shown, not just asserted)

Founder's proposed gate: `(Priority ∈ {4,5}) OR (Criticality ∈ {Amber,Red}) OR (score > 16)`.

**Finding 1 — the score clause is mathematically redundant.** In the region where *both* other conditions are false (Priority ≤ 3 AND Criticality ≤ Orange), the maximum achievable score is `3 × 3 = 9` (bottom-right cell of the Priority≤3/Criticality≤Orange sub-grid). Since 9 < 16, `score > 16` can never independently fire outside the region already covered by the first two conditions — it adds nothing to the union.

**Finding 2 — the remaining two-condition OR is too broad.** `Priority ∈ {4,5}` covers 2 of 5 rows = 10 cells. `Criticality ∈ {Amber,Red}` covers 2 of 5 columns = 10 cells. Overlap = 4 cells. Union = 10 + 10 − 4 = **16 of 25 cells (64%)** — most of the matrix, which actively works against the goal of a *selective* urgent-attention surface and would produce exactly the high false-positive rate the founder was trying to avoid by moving to a 5-point scale in the first place.

### 4.4 Final resolved rule

```ts
// Urgent Attention qualifying rule: score >= 16, uniform across all three per-tier bars.
//
// Why 16 and not 15: Priority(3) x Red(5) = 15 -- a Priority-3 item must NOT qualify for Urgent
// Attention regardless of how severe its Criticality is (explicitly excluded per the founder's
// spec). 16 is the smallest integer cutoff that excludes 3x5=15 while staying a round, simple
// number -- not a data-fitted statistical optimum (this repo has no historical alert-outcome
// dataset to compute one against; this is a principled design cutoff, not a computed one).
export function qualifiesForUrgentAttention(priority: PriorityLevel1to5, criticality: CriticalityBand): boolean {
  return computeScore(priority, criticality) >= 16;
}
```

**Qualifying set**: exactly 4 of 25 cells — **P4×Amber(16), P4×Red(20), P5×Amber(20), P5×Red(25)** — **16% of the grid**.

**Verification that this excludes the known trap case**: P3×Red = 3×5 = 15 < 16 → excluded, correctly, with no special-case logic required — the exclusion falls out of the threshold itself.

**Design note carried forward explicitly (not silently absorbed)**: this rule includes P4×Amber (score 16), which an earlier draft (a named-pair generalization requiring P4 to hit Red specifically) would have excluded. This was a deliberate founder decision made in Round 4, not an oversight.

**Honesty note per evidence discipline**: the choice of 16 (vs. e.g. 17, 18) is a principled design cutoff — the smallest integer that clears the known trap case — not a statistically-fitted optimum. This repository has no historical alert-outcome/false-positive dataset to run an actual precision/recall optimization against. If real usage data accumulates post-launch, this threshold should be revisited empirically rather than assumed correct indefinitely.

### 4.5 Per-tile-type policy layer (how a tile actually gets a Priority/Criticality, not just how scores are compared)

The founder's spec requires every tile's Priority/Criticality to be "based on policy and agentic decision based on policy" — i.e., derived from live data via rules, not hardcoded per widget. This generalizes an existing pattern already in this codebase (`src/services/workflows/enterpriseGoldenPath.ts:75`, `statusWeight: Record<EnterpriseWorkflowStatus, number>`, aggregated into `readinessScore` at line 239; and `workflowEvidence.ts`'s `buildTenantHealthIndicators`, which maps live metrics into `{tone}` via threshold rules like `metrics.pendingApprovals >= 20 ? "danger" : ...`).

```ts
// src/services/dashboard/tilePolicies.ts
export const tilePolicies: TilePolicyRegistry = {
  "overdue-task": {
    tier: 1,
    evaluate: (task: Task) => {
      const daysOverdue = daysSince(task.dueDate);
      const priority = daysOverdue > 7 ? 5 : daysOverdue > 3 ? 4 : daysOverdue > 0 ? 3 : 2;
      const criticality: CriticalityBand =
        daysOverdue > 5 ? "red" : daysOverdue > 2 ? "amber" : daysOverdue > 0 ? "orange" : "green";
      return { priority, criticality };
    },
  },
  "pending-ai-review": {
    tier: 1,
    evaluate: (count: number) => ({
      priority: count > 10 ? 5 : count > 5 ? 4 : count > 2 ? 3 : count > 0 ? 2 : 1,
      criticality: count > 10 ? "red" : count > 5 ? "amber" : count > 2 ? "orange" : count > 0 ? "yellow" : "green",
    }),
  },
  // one entry per tile type -- each pure, independently unit-testable, matching the existing
  // per-function test style in enterpriseGoldenPath.test.ts.
};
```

Each policy is a pure function of live data → `{priority, criticality}`. This is deliberately a small, explicit config table (matching the existing `statusWeight` precedent), not a general rules engine — a rules engine would be over-engineering for the current tile count and contradicts this repo's stated principle of not building abstractions beyond what's needed.

## 6. Architecture

### 6.1 Reusable primitives (verified to exist)

- `src/components/ui/RiskBadge.tsx` (18 lines) — a 3-tone badge (`red`/`amber`/`emerald`, keyed off `high|medium|low|urgent`). **Cannot** represent the new 5-value `CriticalityBand` — reusing it as-is would collapse Yellow and Orange into whichever of Green/Amber they're mapped to, silently losing the distinction the founder's spec requires. A new `CriticalityBadge.tsx` is needed (5-tone sequential ramp: emerald → lime/yellow → orange → amber/dark-orange → red), consistent with R4's banded-heatmap convention.
- `src/components/enterprise/TenantHealthCommandCenter.tsx` — existing tile card shape (icon + tone-colored chip, label, value, detail, link) — the right shape to generalize into the new `ScoredTile` component.
- `src/components/enterprise/index.tsx` — exports `SectionCard`, `EnterpriseBadge`, `DataStateBadge`, `EmptyState`, all reusable as-is for tier containers and "not yet connected" states.

### 6.2 New files

- `src/services/dashboard/tileScoring.ts` — `CriticalityBand`, `PriorityLevel1to5`, `ScoredTile` types; `computeScore`; `qualifiesForUrgentAttention` (§4.4).
- `src/services/dashboard/tilePolicies.ts` — per-tile-type policy registry (§4.5).
- `src/services/dashboard/buildDashboardSnapshot.ts` — orchestrates all existing + new hook outputs into the full `ScoredTile[]`, tier by tier, with honest `dataState: "not-connected"` entries for unbuilt sources.

### 6.3 Modified files

- `src/features/dashboard/DashboardSection.tsx` — replace the flat JSX stack with `<UrgentAttentionBarStack>` + three `<DashboardTier tier={1|2|3}>` sections consuming `buildDashboardSnapshot`'s output. All existing hooks (`useLiveWorkspaceMetrics`, `useEnterpriseGoldenPath`, `useAuditLogCount`, `usePendingAiReviewCount`, `useSocialAlertsStatus`, `useWorkflowTimeline`) are preserved as live-data inputs, not refetched.

### 6.4 Live re-flow mechanism (concrete)

Score is derived purely from already-fetched data at render time — no separate polling loop needed. Re-flow is `tiles.filter(t => t.tier === n).sort((a,b) => b.score - a.score)`, memoized with `useMemo`. Tiles carry stable `id`s, rendered with `key={tile.id}` in a CSS grid (`grid-template-columns: repeat(auto-fill, minmax(...))`), row-major reading order, **not** `position: absolute` corner-pinning. This resolves the R6 tension directly: highest-score tiles land first in reading order (= top-left cell in the first row for LTR layouts, which *is* left-central for row one), satisfying "most prominent, closest to natural start" without the eye-tracking study's flagged corner-pinning underperformance. If `framer-motion` is already a dependency, its `layout` prop can animate re-flow transitions (verify in `package.json` before committing to this in Phase 1; ship without animation if absent, treat as a 1.5 polish item).

### 6.5 UI decision: band-first, number-secondary (per R2/R4)

Every tile shows its Criticality band as the dominant visual element (colored `CriticalityBadge`, e.g. "Red · P5"), with the literal numeric score available as a smaller secondary label — never the raw number as the headline. This matches ITSM/GRC precedent (R2, R4) while still keeping the score genuinely computed and inspectable (e.g., for debug/export).

## 7. Ways this redesign improves UX (beyond fixing the tier-weighting inversion)

1. **Faster time-to-critical-information.** Today, an urgent HITL item or SLA breach is only visible if the user scrolls to its fixed position in a 661-line hardcoded stack. The triple stacked urgent bar surfaces the top ~16% of items, cross-tier, at the very top of the screen — no scrolling required to know if anything needs attention right now.

2. **Domain-separated urgency, not one undifferentiated feed.** Because the urgent bar is 3 separate stacked strips (one per tier) rather than one merged list, a user can tell at a glance *which kind* of urgent item they're looking at (a performance/ops issue vs. an AI-infra issue vs. a compliance issue) without reading each item — the domain is encoded by which bar it's in, reducing per-item cognitive parsing (directly consistent with R6's finding that ordered, predictable layout structure reduces cognitive load, p<0.001).

3. **Self-prioritizing content instead of static ordering.** In the current dashboard, an item's visual prominence is fixed by where an engineer happened to place it in JSX, regardless of how urgent it actually is today. The score-driven re-flow means a newly-critical item (e.g., a lead that just went cold, a compliance item that just breached) automatically becomes more visually prominent the moment its underlying data changes — no manual dashboard curation, ever.

4. **Consistent visual vocabulary for "how bad is this" across the whole product.** A single `CriticalityBadge` band (Green/Yellow/Orange/Amber/Red) applied uniformly across all three tiers means a user learns one color language once and reuses it everywhere on the page, rather than each section inventing its own ad hoc status treatment (today's dashboard mixes tone conventions across its ~12 different sections).

5. **Honest degraded states build trust instead of eroding it.** Because unbuilt data sources (social monitoring, CRM, calendar, financial thresholds) render explicit "not connected yet" placeholders rather than being silently omitted or faked, users get an accurate mental model of what AXXESS can and cannot yet see — consistent with this codebase's existing anti-fabrication discipline (`DEMO_DATA_LEAKAGE_AUDIT.md` pattern), and avoiding the worse failure mode of a dashboard that looks complete but is quietly wrong.

6. **Compliance stays visible without dominating.** Per R5, most SaaS competitors bury compliance/audit entirely in Settings. Keeping it as a real, scored Tier 3 (not hidden, but also not competing for the top-of-screen with performance content) gives AXXESS's compliance-forward positioning real visibility while still respecting that most users, most of the time, care about Tier 1 content first — the score-driven urgent bar is what pulls a genuinely critical Tier 3 item (e.g., a Red audit objection) up to top-of-screen visibility exactly when it matters, without permanently inflating Tier 3's footprint.

7. **Reduced "false-urgency fatigue."** The deliberate `score >= 16` threshold (16% of the grid, not 64%) means the urgent bar stays meaningfully rare — when something does appear there, users can trust it's genuinely worth immediate attention, rather than habituating to an over-triggered alert bar and learning to ignore it (a well-known alert-fatigue failure mode in ops/monitoring UX, and the exact failure the founder's own "false negatives and false positives" reasoning in Round 3 was steering away from).

## 8. Phased roadmap

### Phase 0 — Scoring/policy engine (foundation; blocks everything else)
Build `tileScoring.ts` and `tilePolicies.ts` in isolation, fully unit-tested, with zero UI dependency. No visible product change yet.

### Phase 1 — Layout + re-flow engine, wired to real data that exists today
Build `buildDashboardSnapshot.ts`, the tier/bar UI components, and restructure `DashboardSection.tsx`. Populate tiles from real sources only (tasks, meetings, approvals, projects, audit logs, RAG health, golden path, AI spend). All founder-requested sources without real data render honest not-connected placeholders. **This phase alone corrects the tier-weighting inversion and ships the full scoring/layout/urgent-bar mechanism** — later phases only add data, they don't change the engine.

### Phase 2a — Mail inbox tile
Extend `gmailSelectedMessage.ts`/`microsoftGraphMailbox.ts` into a real "mails needing reply" repository + count; register a Tier 1 policy.

### Phase 2b — CRM leads/deals
New `Lead`/`Deal` domain entities + repository (likely paired with, not replacing, `Stakeholder`); new Tier 1 policy.

### Phase 2c — Social monitoring
Build the repository layer `useSocialAlertsStatus.ts` currently lacks (`social_alert_events`/`social_alert_rules`); extend to LinkedIn/Meta/WhatsApp Business.

### Phase 2d — Calendar + Zoom/Gmeet
Net-new integrations; no existing plumbing to extend.

### Phase 2e — Financial thresholds
New bank-account/budget domain entities + repository; Tier 3 policies.

Each Phase 2 item adds policy entries to the existing `tilePolicies` registry and a data hook — the Phase 1 engine requires no changes to absorb them. This is the direct payoff of building the scoring engine generically up front rather than per-source.

## 9. Risks and tradeoffs (explicit, not hidden)

- **Combined bar-stack height budget.** Three permanently-reserved fixed bars would cost real vertical space on smaller viewports. Mitigated by: (a) each bar independently collapses to zero height when its tier has no qualifying tiles, (b) each bar is capped to a single row with horizontal scroll for overflow rather than vertical growth, (c) the content area's top offset must dynamically track the stack's actual rendered height (via `ResizeObserver` or equivalent), since it changes as bars collapse/expand — this is a required Phase 1 implementation detail, not optional polish.
- **`position: fixed` top offset vs. existing page chrome.** Must be verified against `PageShell`'s actual header height before implementation — a global nav/header may already occupy `top: 0`.
- **3-tier vertical structure is a genuine, unprecedented design bet** (R7) — no major BI vendor structures a dashboard this way. Recommend post-ship user testing rather than treating the structure as pre-validated; not a blocker to shipping Phase 1.
- **`score >= 16` is a principled cutoff, not a statistically-fitted one** (§4.4) — revisit empirically once real usage/false-positive data exists.
- **P4×Amber now qualifies for the urgent bar** where an earlier draft would have excluded it — confirmed as a deliberate founder decision (§2, Round 4), not an error, but worth re-confirming after live use if it feels too permissive in practice.
