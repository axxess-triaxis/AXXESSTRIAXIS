# Tenant Partitioning -- Repository Boundary Audit (Sprint TP-2, 2026-07-28)

Date: 2026-07-28
Governance source: Codex's "Sprint TP-2" prompt.
Method: read the actual query-construction code for the shared repository factory functions
(`listResource`, `getResourceById`, `updateResource` in `src/repositories/supabaseEnterpriseRepositories.ts`),
confirmed which repositories are built from them, then individually read the repositories that are
**not** built from the shared factory (AI reviews, approvals/workflow actions, audit logs' write
path, dashboard metrics).

## Key Architectural Finding

Most tenant-scoped repositories in this codebase are generated by two factory functions,
`createTenantRepository`/`createMutableTenantRepository`, which both route every read through
`listResource`/`getResourceById` and every write through `updateResource`
(`supabaseEnterpriseRepositories.ts:469-544`). These factories apply tenant scoping **twice, at
two independent layers**:

1. **Application-level query filter**: `applyRepositoryQuery` (line 369) sets
   `organization_id=eq.${scope.organizationId}` on every list/get query, and both `updateResource`
   (line 533) and the create path set the same filter on writes, **unless the caller's role is
   `Super Admin`** (an intentional, named exception -- see Risk section below).
2. **Row Level Security**: every direct-to-Supabase request uses `Authorization: Bearer
   ${scope.accessToken}` -- the real, authenticated user's own JWT, not a service-role key -- so
   RLS policies also apply independently of the application-level filter.

For **updates specifically**, the `id=eq.<id>` and `organization_id=eq.<scope.organizationId>`
conditions are combined in the *same* PATCH request (line 532-533) -- a cross-tenant update
attempt matches zero rows and throws, rather than silently succeeding or silently no-op'ing.

This means the repository-boundary question for the ~10 resources built from this factory
(`organizations`, `users`, `programs`, `projects`, `tasks`, `stakeholders`, `documents` + its four
sibling tables, `knowledge_articles`, `meetings`, `notifications`, `audit_logs`) reduces to one
question, verified once: does the factory itself enforce scoping correctly? **Yes, with one named
exception (Super Admin).**

## Risk: The Super Admin Exception

`scope.role !== "Super Admin"` is the one place the application-level `organization_id` filter is
**not** applied on reads or writes for factory-based repositories. This is very likely an
intentional design decision (a platform-wide Super Admin role needs cross-tenant visibility for
support/ops), but it means **RLS is the sole enforcement mechanism for that one role**, with no
application-level backstop. This is exactly the scenario A-10 (the two-tenant isolation harness,
still `Blocked` on a non-production database to run against) exists to prove or disprove. **Not
resolved by this sprint** -- named explicitly as a TP-3 prerequisite below.

## What Was Not Individually Re-Verified This Sprint

- Every one of the ~40+ API routes under `src/app/api` was not read line-by-line; the dominant,
  shared patterns (the `/api/repositories/[resource]` gateway, the AI review route, the
  workflow-action repositories) were verified with concrete code evidence, and this audit's
  confidence rests on those shared code paths being genuinely shared (confirmed via `grep` showing
  which files import which factory functions), not on having read every consuming route
  individually.
- The actual Postgres RLS policy definitions themselves were not read or run this sprint (no
  database access from this environment) -- every "RLS assumption" claim above is exactly that, an
  assumption based on the application code's own comments and JWT-based auth pattern, not a
  verified policy read. This is precisely what A-10's isolation harness exists to close.
