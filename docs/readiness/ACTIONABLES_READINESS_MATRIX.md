## Operating Rules

Every actionable must be reviewed after every sprint.

An actionable can be marked `Yes` only if all of the following are true:

- Implementation exists.
- Verification evidence exists.
- The relevant user journey works or the external blocker is documented.
- Documentation is updated.
- Confidence is at least 80%.

### Integration Maturity Tiers -- Standing Convention (2026-08-08)

The plain `Yes`/`Blocked`/`No`/`Deferred`/`Partial` vocabulary above is necessary but too coarse
for any row that bundles multiple distinct connectors/providers (e.g. A-70's Calendar/Drive/Zoom/
Teams, A-77's Sheets/Docs/Slides/WhatsApp/Linear/GitHub/X) -- collapsing several connectors at very
different depths into one blended `Partial X%` reads, to an outside investor or customer, as if
every named integration is equally shallow "surface area," which misrepresents real, meticulous,
conservatively-verified depth on the ones that are actually done. Per the founder's explicit
instruction (2026-08-08), every row or sub-item with an integration/connector surface is now tagged
with one of these six tiers, stated inline next to the connector's name, not blended into a single
row-level percentage:

1. **Fully complete and tested** -- code shipped, production credentials configured, AND a live
   end-to-end connection independently confirmed (a real toast/callback-success screenshot or
   equivalent evidence exists, not just "should work").
2. **Complete but not user-tested** -- code shipped, production credentials configured, deployed,
   but no live human click-through confirmation exists yet.
3. **Almost complete** -- code shipped, credentials configured, live testing has reached the final
   step, and only one small, specific, *named* gap remains (e.g. one missing redirect-URI field,
   one missing OAuth scope) -- the remaining work is a single external configuration action, not
   further engineering.
4. **Partial** -- real, substantive work remains beyond a single final config step (some but not
   all of a multi-part connector is done, or more than one distinct gap remains).
5. **Coded only** -- the connector contract/OAuth code exists in the codebase, but zero production
   credentials are configured and it has never been tested, live or otherwise.
6. **Fully pending** -- no code exists yet for this connector; it exists only as a named roadmap
   item.
7. **Fully/partially integrated but currently irrelevant due to pricing/product decision** --
   distinct from tiers 1-6, which describe engineering completeness, and distinct from `Deferred`
   in the top-level vocabulary, which implies a technical blocker parked for later. This tier is
   for connectors where the *technical* work is done or mostly done, but a **business-level
   decision** (cost, plan tier, provider switch) -- not a technical gap -- is what makes it
   currently unusable or moot. Examples on record (2026-08-08): Microsoft Entra/Teams/Outlook
   (technically wired, but the Azure subscription funding it was cancelled -- a cost decision, not
   a code blocker); Twilio phone-OTP (works and is live-tested end to end, but the Trial account's
   single-verified-number limit makes it 0% usable for real pilot users -- a plan-tier limitation);
   Elastic Mail (integration existed, but superseded outright by a provider switch to Resend -- a
   product decision, not a failure). Do not mark something in this tier as `Blocked` or `Deferred`
   without also naming the specific business decision responsible, so a reader can tell it apart
   from a genuine unresolved technical gap.
8. **Fully integrated but not functional (Pricing/Credits)** -- distinct from tier 7: not a
   deliberate decision to deprioritize, but an active, ongoing functional impairment. The
   connector/provider is fully wired, credentials are configured, and real calls are being made --
   but they currently fail or are constrained because the account's paid tier, credit balance, or
   rate limit is insufficient. Example on record (2026-08-08): **OpenAI** (real calls are made,
   confirmed via the honest 429 fallback text seen live this session -- `openAiProvider.ts`'s
   `request failed (429)` path -- but the account's current rate/quota limit means calls
   intermittently or currently fail; root cause of the 429 itself remains undiagnosed, see A-81).
   **OpenRouter** -- same class, credential/routing code complete, functional status gated on
   account credit/tier, not independently re-verified this pass.
9. **Fully integrated but not functional (Data/volume)** -- the integration works technically
   (events are received, dashboards render), but is not yet functionally useful because there
   is not enough real user/usage volume flowing through the product for it to produce meaningful
   signal -- a product-maturity/traction problem, not a technical, pricing, or deliberate-decision
   problem. Example on record (2026-08-08): **Mixpanel**, **PostHog** -- both technically wired and
   receiving events per this program's analytics-event-taxonomy work (see A-22), but with the
   product's current real user count, neither yet has enough volume to produce meaningful
   dashboards/insights.
10. **Part of roadmap but scrapped** -- a connector/integration that was previously planned or
    named as intended work, then explicitly decided against, rather than merely deferred or not
    yet started. **Currently no entries (2026-08-08)** -- tier defined for future use, nothing in
    this matrix qualifies as of this update.

These tiers apply *within* a row, per connector -- they do not replace the row's own overall
`Yes`/`Blocked`/`Partial`/etc. status, which still governs whether the row as a whole counts as
closed in the open/closed tallies elsewhere in this program's reporting.

Founder acceptance loop for live/user-facing items:

1. Claude Code / Codex first checks off the item as code/test/responded.
2. The founder walks through the deployed product live.
3. Any issues, bugs, stale data, placeholders, dead ends, confusing copy, routing failures, missing
   audit rows, or tenant/demo leakage are logged as actionables.
4. Claude Code / Codex debugs and performs the required remediation: UX optimization, stale-data
   cleanup, placeholder cleanup, screen/flow transition fixes, routing fixes, failure-state fixes,
   and any other required rectification.
5. The founder performs any required re-check and explicitly signs off before the issue is closed.
6. Claude Code / Codex closes the issue only after documenting the whole process, steps, evidence,
   decisions, and rationale in a closeout document.

If implementation exists but live proof does not, status remains `No`.

## P0 Correction: Public Entry Split (2026-07-24, HITL "Attempt 4")

**Root-caused and fixed.** The two-sprint-old "Investor Preview's Continue to workspace is broken" / "root domain lands on a stale, dead-end authenticated-looking page" defects (first flagged in the Sprint 1 pre-work walkthrough above, never previously root-caused) were reproduced live by the HITL and diagnosed to a precise mechanism: `/auth`'s "already authenticated" branch treated a demo/investor mock session (`source: "mock-rbac"`, set by clicking "Open investor preview") exactly like a real one, so a visitor who had ever opened Investor Preview in a browser saw "Signed in as Ananya Rao" on every future `/auth` visit regardless of intent -- including a genuine "Sign In" click from the public site. Full detail: `docs/readiness/P0_PUBLIC_ENTRY_INVESTOR_BETA_SPLIT_2026_07_24.md`.
