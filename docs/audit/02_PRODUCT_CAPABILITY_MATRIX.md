# Phase 2 -- Product Capability Audit

Every meaningful product capability, traced into actual implementation code rather than accepted from documentation claims. Produced by 5 parallel research sweeps, each instructed to classify findings using VERIFIED / CORROBORATED / CLAIMED / INFERRED / UNVERIFIED / NOT FOUND IN AVAILABLE EVIDENCE, cite exact file paths, and treat `docs/readiness/*.md` as pointers only, never as evidence in themselves. 48 capabilities covered across 5 clusters: Identity & Access, Core Work Product, Knowledge & AI/Agentic, Platform & Integrations, Operations & Enterprise Readiness.

**How to read this document:** the tables below are close to verbatim from each research sweep -- they are the evidence. The section immediately below is this document's own synthesis across all 5, written after reading all five reports together, and is where the most consequential findings live. Read that first; the tables are for verifying and drilling into any specific line.

---

## Cross-cutting synthesis -- the findings that matter most

**1. The most sophisticated-looking permission layer in the codebase is dead code.** `src/security/tenantGuard.ts` and the `EnterprisePermission`/`hasEnterprisePermission` model in `enterpriseIam.ts` are fully implemented and unit-tested, but have zero call sites in any API route or server module (confirmed by grep across all non-test `src` files). Real authorization runs through two other, simpler mechanisms: Postgres RLS (`has_any_role`/`is_org_member`) and a narrower `canManageOrganization` check used in a handful of admin routes. This is not a capability gap in the "feature is missing" sense -- it's a gap between code that exists and code that actually runs on a real request.

**2. Tenant-isolation "tests" are almost entirely static string assertions against migration SQL text, not runtime proof.** 14 files under `src/security/{rlsPolicies,sprint*RLS}.test.ts` do `readFileSync` on a migration file and assert it `.toContain(...)` a policy definition -- they verify the SQL was *written*, not that it *behaves correctly*. The one file that would actually prove cross-tenant isolation live, `supabase/tests/rls_persona_tests.sql`, has every real assertion commented out -- it is a template, not a working test. CI (`bitrise.yml`'s `supabase_rls_tests` job) only checks that this file exists; it does not execute it against a live database. Given this is the single most safety-critical property for a multi-tenant SaaS, this is the most material finding across the whole audit so far: **there is no automated, currently-executing proof that tenant A cannot read tenant B's data.** The RLS *policy design* itself is sound and well-evidenced (near-universal `organization_id` scoping, RLS enabled on effectively all 109 tables per Phase-2's Ops cluster finding) -- what's missing is the test that would catch a regression in it.

**3. There is no real embedding model or vector database anywhere in the codebase.** "RAG" retrieval runs on a 16-dimension token hash-sketch (`deterministicEmbeddingProvider`, literally named `local-hash-embedding`) scored via dot-product over an unindexed Postgres `jsonb` column -- no OpenAI/Cohere embeddings call, no pgvector, no Pinecone/Weaviate. Real, permission-filtered retrieval of actual tenant documents does happen (verified, with dedicated cross-tenant isolation tests) -- but calling this "vector search" or "semantic search" would overstate what's running.

**4. Only 3 of 8 named "AI providers" make real model calls.** OpenAI and OpenRouter-routed Kimi K2/DeepSeek V3 have real, credentials-gated adapters with real cost tracking. Anthropic, Google, xAI, Falcon, and Jais are named, priced, and routable in policy, but their adapter returns canned placeholder text even when API keys are present -- no SDK or fetch call to any of them exists anywhere in `src/`. Similarly, RAG's "generation" step defaults to a local extractive summary (not an LLM at all) unless a live provider is configured and actually responds -- the code caps confidence and labels this explicitly for exactly that reason.

**5. Agent tool-calling is real but one-directional, and approval-gating is real but partial.** External AI agents (Claude Desktop, etc.) can genuinely call AXXESS's tools through a real MCP JSON-RPC server that writes to live Supabase tables -- this is not a mock. But AXXESS's own chat assistant never autonomously invokes a tool itself (no evidence found of that internal loop). Of the 8 registered agent tools, 4 (including `create_task`, which writes real data) execute immediately with zero human approval by explicit design; the other 4 genuinely block pending a human decision. No prompt-injection mitigation was found -- retrieved document text is concatenated directly into prompts sent to live providers, unsanitized.

**6. "CRM" is not a real product surface, and there is no configurable workflow engine.** The CRM nav item re-exports the generic workspace page; a separate leads table exists but only feeds dashboard counters, and its own update function is unreachable from any route (dead code except its unit test). What's called a "workflow engine" is either a fixed 8-step onboarding journey (same for every tenant, real progress-tracking) or a fully hardcoded demo-only array -- no rule/trigger/automation builder or per-tenant customization mechanism exists anywhere.

**7. Mobile has three parallel, unreconciled strategies, none store-ready.** A real Expo/React Native app, a Capacitor WebView wrapper of the full product, and a separate Capacitor wrapper scoped to Web Lite all coexist. None of the Capacitor apps have their native projects actually committed to git -- `settings.gradle`, `MainActivity`, `.xcodeproj` don't exist in the tree; CI regenerates them from scratch every run via `cap add android/ios`. iOS additionally has no signing credentials configured anywhere checkable in-repo.

**8. Billing is a placeholder with only credential-vault plumbing behind it.** No live Stripe/Paddle checkout, subscription, or webhook logic exists, despite a five-tier pricing narrative in business documentation. The payments page literally renders a placeholder component.

**9. Real production incidents are visible directly in the migration history and code comments, and this is unusually strong corroborating evidence** -- not marketing copy. A broken audit-trigger CASE expression that failed every write to core tables until fixed; missing `service_role` grants that broke tenant provisioning; a `NOT NULL` constraint with no default that broke every new signup until a trigger was added; a documented refresh-token race that could silently log out a legitimate session. These read as genuine engineering incident logs.

**10. The codebase is unusually self-honest in its own comments, repeatedly, across every cluster.** Explicit in-code admissions found independently by all 5 sweeps: "AXXESS has no dedicated Reminder type," "No live approvals repository exists yet" (stale but illustrative of the pattern), "a SAFE SCAFFOLD, not a built native project," "Configuration only -- no live checkout flow is wired yet," "Neither RAG path... calls a real external language model" (context-dependent), and the Zoom connector's dated, multi-day debugging log ending in an unresolved error. This pattern is itself evidence worth weighting: where this audit could not independently verify a claim, the codebase's own self-assessment tends to run conservative, not inflated.

## New founder question raised by this phase

### Q-004

**Category:** Enterprise readiness / security posture

**Question:** The RLS *policy design* across all ~109 tenant tables looks sound and well-evidenced (near-universal `organization_id` scoping, RLS enabled, JWT-scoped PostgREST calls rather than service-role bypass). But this audit found no automated test that actually executes against a live database to prove tenant A cannot read tenant B's data -- the 14 existing "RLS test" files only assert that policy SQL text was written, and the one file designed to be a real live-persona test has every assertion commented out. Is this a known, accepted gap (e.g., isolation has been manually/informally verified some other way not captured in this repo), or is this a genuine, previously-unflagged gap that should be treated as a priority fix?

**Why this matters:** This is the single highest-stakes correctness property for a multi-tenant SaaS selling to enterprise/government buyers. It directly affects Phase 5's Enterprise Readiness scoring and Phase 16's Red Team analysis, and any external claim about tenant isolation should not rest on this repo's current test suite without qualification.

**Current evidence:** `src/security/rlsPolicies.test.ts` and 13 sibling files use `readFileSync`+`toContain` against migration SQL text. `supabase/tests/rls_persona_tests.sql` has every real assertion commented out (a template, not a working test). `bitrise.yml`'s `supabase_rls_tests` CI job only checks the file exists.

**Possible interpretations:**
A. Isolation has been informally/manually verified (e.g., via the `TWO_TENANT_ISOLATION_HARNESS_EXECUTION_2026_08_06.md` doc referenced elsewhere in this repo, not yet read/verified by this audit) and this is a documentation/CI-automation gap, not a correctness gap.
B. This is a genuine, previously-unflagged testing gap that should be prioritized.

**What evidence would resolve it:** Founder confirmation, plus pointing this audit at any existing manual isolation verification (e.g. the two-tenant isolation harness doc mentioned above) so it can be independently checked in a later phase.
